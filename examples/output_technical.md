## 卡片 1：索引的作用
**核心知识**：索引是一种加速数据检索的数据结构，用来避免大数据表下的全表扫描。
**简明解释**：没有索引时，数据库必须逐行比对（全表扫描），表越大越慢；索引通过预组织的结构让查询能快速定位目标行。
**例子 / 自测**：为什么在百万行表上按未索引列过滤会明显变慢？

## 卡片 2：B+ 树索引结构
**核心知识**：主流索引多采用 B+ 树——一种平衡多路搜索树，数据只存于叶子节点且叶子间以指针相连。
**简明解释**：由于所有数据集中在叶子层，且叶子节点顺序串接，B+ 树既能保证查找稳定，又让范围查询（如 BETWEEN、排序）非常高效。
**例子 / 自测**：为什么"查 100~200 之间的记录"用 B+ 树比哈希索引更合适？

## 卡片 3：聚簇索引与非聚簇索引
**核心知识**：聚簇索引决定数据行的物理存储顺序（每表仅一个），非聚簇索引的叶子节点存的是指针或聚簇键，查找常需"回表"。
**简明解释**：聚簇索引与数据本身合一，因此按它查找最快；非聚簇索引是独立的"目录"，找到位置后往往还要回到主表取完整行，这一步叫回表。
**例子 / 自测**：为什么通过非聚簇索引查"未包含在索引中的列"会更慢？

## 卡片 4：索引的代价（读写权衡）
**核心知识**：索引以空间换时间——加速读查询，但占用存储并拖慢增删改。
**简明解释**：每个索引都要额外磁盘空间，且写操作（插入/更新/删除）需同步维护所有相关索引，所以索引并非越多越好。
**例子 / 自测**：一个写多读少的表，盲目加大量索引会带来什么问题？

## 卡片 5：最左前缀原则
**核心知识**：复合索引 (a, b, c) 只有在查询命中最左列（如 a，或 a+b）时才有效；跳过最左列则索引通常失效。
**简明解释**：复合索引按列顺序构建，优化器只能从最左列开始匹配；只查 b、c 而漏掉 a，索引便无法被利用。
**例子 / 自测**：对 (a,b,c) 索引执行 `WHERE b=1 AND c=2`，索引能否生效？为什么？

## 卡片 6：覆盖索引避免回表
**核心知识**：若查询所需字段全部包含在某索引中，数据库无需回主表取数，即为覆盖索引，可进一步提升性能。
**简明解释**：回表是额外 I/O；当索引本身已经"覆盖"了 SELECT 的列，查询在索引层即可完成，省去访问主表的开销。
**例子 / 自测**：`SELECT id, name FROM t WHERE name='x'` 在 (name, id) 索引下能否避免回表？

## 卡片 7：常见索引失效诱因
**核心知识**：对索引列做函数运算、隐式类型转换、或使用前导通配符 LIKE（如 '%abc'），都会让优化器放弃索引。
**简明解释**：这些写法破坏了索引列的原始有序可比性，优化器无法利用索引定位，只能退化为全表扫描。
**例子 / 自测**：`WHERE DATE(created_at)='2024-01-01'` 为什么可能导致索引失效？

## 卡片 8：如何选择索引列
**核心知识**：优先为高区分度、且频繁出现在 WHERE / JOIN / ORDER BY 中的列建索引；低区分度列通常不适合。
**简明解释**：高区分度列能让索引快速收窄结果集；而这些列若又是常用过滤条件，建索引收益最大。低区分度（如"性别"）列过滤能力差，建索引意义不大。
**例子 / 自测**：对"是否删除"这种只有两值的标记列建索引，通常为何收益有限？
